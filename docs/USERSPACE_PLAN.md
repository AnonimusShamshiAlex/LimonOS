# План: от «lima/apt показывает честную заглушку» к настоящему запуску программ

Это не план «добавить nmap». Это план добавить в LimonOS то, чего у неё сейчас
физически нет: загрузку и исполнение чужого машинного кода. Каждая фаза —
отдельный, самостоятельно тестируемый кусок. Фазы идут строго по порядку:
без предыдущей следующая не имеет смысла.

Текущее состояние ядра (проверено чтением kernel/*.c на 2026-10-26):
- один кольцевой уровень — всё ядро работает в ring0, нет ring3 вообще;
- нет таблиц страниц на процесс — `mem.c` это физический аллокатор страниц
  (`pmm_alloc`) плюс куча ядра (`kmalloc`), общая на всех;
- GDT (`gdt.c`) — только два дескриптора: код/данные ring0, нет ни
  пользовательских сегментов, ни TSS;
- IDT (`idt.c`) обрабатывает исключения/IRQ, но нет обработчика системного
  вызова и некуда ему вести — процессов нет;
- `store.c`/`vfs.c` хранят файлы только в ОЗУ (Memoria), запись на диск не
  реализована — не проблема для фазы 1-4, важно для «поставил — осталось
  после перезагрузки», это отдельная задача.

## Фаза 1 — ELF64: разбор и проверка файла ✅ сделано в этом патче
Файлы: `kernel/elf.h`, `kernel/elf.c`, тест `tests/elf_host.c` (+ фикстура
`tests/tiny_static.S` — настоящий статический ELF64, собранный системным `ld`,
а не байты, которые мы сами придумали «похожими на ELF»).

Что умеет: проверить магию/класс/архитектуру/тип, разобрать program header'ы,
собрать список PT_LOAD сегментов (адрес/размер в памяти/что брать из файла),
отклонить обрезанный файл, файл с пересекающимися сегментами, файл с точкой
входа вне исполняемого сегмента, PIE (`ET_DYN` — его поддержим позже, статика
проще и её достаточно для первого шага).

Чего не умеет и не должен: ничего не грузит в память, ничего не выполняет.
Это чистая функция над байтами — поэтому её можно (и нужно) было протестировать
на хосте прямо сейчас, без эмулятора. Тест гоняет настоящий бинарь,
слинкованный `ld`, и набор намеренно битых копий.

Команда: `tests/run_host_tests.sh` (добавлен раздел «ELF64-загрузчик, фаза 1»).

## Фаза 2 — Таблицы страниц на процесс ✅ сделано в этом патче
Файлы: `kernel/vmm.h`, `kernel/vmm.c`, тест `tests/vmm_host.c`.

Что умеет: `vmm_map`/`vmm_unmap`/`vmm_translate` — полноценный обход 4-уровневых
таблиц x86_64 (PML4→PDPT→PD→PT, страницы по 4 КиБ) с созданием промежуточных
таблиц по требованию; `vmm_share_upper_half` — связывает верхние 256 записей
PML4 (индексы `VMM_SPLIT_INDEX..511`, это канонический диапазон ядра/HHDM)
между пространством ядра и пространством процесса так, как это делает Linux:
не разовая копия, а общие таблицы — если ядро потом добавит ещё одно
отображение в уже существующей верхней ветке, процесс увидит его сам, без
повторного вызова.

Как протестировано: вся логика обхода/создания таблиц получает функцию
аллокации страницы и функцию "физический адрес → куда писать прямо сейчас"
параметрами (`vmm_alloc_page_fn`/`vmm_p2v_fn`), а не лезет в `pmm_alloc`/HHDM
напрямую. В `tests/vmm_host.c` вместо реальной физической памяти — обычный
`malloc`-буфер, который играет роль физической арены. Это честно: проверена
сама логика индексации/создания/расшаривания таблиц (отображения на разных
уровнях не мешают друг другу, `unmap` снимает ровно одну запись, нехватка
памяти у аллокатора не роняет код, а возвращает ошибку, расшаренная верхняя
половина — живая связь, а не снимок). НЕ проверено и не может быть проверено
в этой среде: собственно `mov cr3` на реальном процессоре/эмуляторе — здесь
нет ни QEMU, ни сети, чтобы его поставить.

`vmm_read_cr3`/`vmm_load_cr3`/`vmm_invlpg` в `kernel/vmm.h` — три строки
настоящего ассемблера по спецификации x86_64 (Intel SDM vol.3), но ни одна из
них пока НЕ вызывается из остального ядра (`kmain` их не трогает) — ровно по
той же причине, что RTL8139/ATA в 1.1 остались "написано по спеке, не
запускалось": это можно по-настоящему проверить только на эмуляторе/железе
у тебя. Включать их в реальный boot-путь — задача Фазы 3, и именно там это
впервые получит проверку не только на бумаге.

## Фаза 3 — GDT/TSS и переход в ring3 ✅ код написан; хост-часть проверена, ring3 на железе ещё НЕ запускался
Файлы: `kernel/ring3.h` (чистая часть), `kernel/gdt.c`, `kernel/usermode.S`, `kernel/user.c`,
`kernel/user.h`, хук в `kernel/interrupts.c`, команда `ring3` в `kernel/shell.c`,
тест `tests/gdt_host.c`.

Что сделано:
- GDT: null / код ядра 0x08 / данные ядра 0x10 / данные пользователя 0x18 (селектор 0x1B) /
  код пользователя 0x20 (селектор 0x23) / TSS 0x28 (16 байт). Порядок выбран так, чтобы в Фазе 4
  можно было включить `syscall/sysret` без перестройки GDT (STAR[63:48]=0x10 даёт SS=0x18, CS=0x20).
- TSS (104 байта): `rsp0` = статический стек ядра 16 КиБ, карты портов нет (IOPL=0, in/out из ring3 запрещены);
  `ltr 0x28` в `gdt_init`.
- `user_enter` (asm): сохраняет callee-saved регистры/rsp/rflags ядра, грузит CR3 пользовательского
  пространства, `iretq` по кадру (rip, cs=0x23, rflags с IF, rsp, ss=0x1B). `user_resume` (asm) —
  аварийный возврат: восстанавливает контекст и «возвращается» из `user_enter` с кодом.
- `isr_handler`: исключение из ring3 больше не паникует ядро, если идёт сеанс `user_run()` —
  состояние программы снимается и управление возвращается в ядро; исключение в самом ядре — паника как раньше.
  IRQ0 из ring3 после EOI проверяет дедлайн и отбирает управление у программы (так работает и защитный
  таймаут 1 с: ring3-программа не может подвесить ядро).
- Процесс: свой PML4 (нижняя половина своя, верхняя общая с ядром — `vmm_share_upper_half` из Фазы 2),
  код на 0x400000 (USER, без записи), стек на 0x7FFFFFFFE000 (USER+WRITE). NX не ставится: он требует EFER.NXE,
  а включил ли его загрузчик — не проверено.
- Страницы процесса выделяются один раз и переиспользуются (у `pmm` пока нет `pmm_free`).

Три проверки (команда `ring3`):
1. `hlt` в ring3 → ждём #GP(0), CS=0x23, SS=0x1B, RIP=0x40000C, RAX=RCX=«LIMONOS3» (push/pop через стек пользователя), RSP=вершина стека;
2. `mov rbx,[0xFFFFFFFF80000000]` в ring3 → ждём #PF, код ошибки ровно 0x5 (страница есть, прав нет, из ring3, чтение), CR2=0xFFFFFFFF80000000;
3. `jmp $` в ring3 → ждём возврат по таймеру: CS=0x23, RIP=0x400000, прошло >= 20 тиков.

Что проверено на хосте (`tests/gdt_host.c`, ASan/UBSan):
дескрипторы побитово (канонические значения + независимый декодер), TSS-дескриптор и раскладка TSS,
порядок селекторов под SYSRET, кадр `iretq` (включая отказ для некано­нических/ядерных rip/rsp, порядок
полей = хвост `struct regs`), разбор кода #PF, бит USER на ВСЕХ уровнях таблиц у пользовательских страниц и
его отсутствие у страниц ядра, неизменность карты ядра при отображении пользовательских страниц,
реальные байты ring3-программ из `usermode.S` (опкоды и смещения), и что функции проверки результата
принимают ожидаемое и отвергают порчу любого поля (проверено мутациями кода).
`make` ядра с реальными флагами — без единого предупреждения; дизассемблирован `gdt_init`
(размер GDT 0x38, лимит TSS 0x67, `lgdt`/`retfq`/`ltr 0x28` — как задумано).

Что НЕ проверено (в этой среде нет ни QEMU, ни KVM, ни сети): всё, что исполняет процессор —
`lgdt/ltr`, `mov cr3`, `iretq` в ring3, переключение на стек TSS, `user_resume`. Критерий успеха Фазы 3 —
три строки `[OK]` от команды `ring3` на QEMU/железе у тебя. Если не так:
- виртуалка перезагрузилась (triple fault) → `qemu-system-x86_64 -cdrom LimonOS.iso -m 256M -d int,cpu_reset -no-reboot`,
  последнее исключение перед сбросом покажет, где именно;
- на экране паника ядра с номером исключения → скажи номер, код ошибки, RIP/CS из паники;
- `[ПРОВАЛ]` с числами под строкой → пришли эти числа, они показывают, какой из ожидаемых пунктов не сошёлся.

## Фаза 4 — Системные вызовы ✅ код написан; хост-часть проверена, `int 0x80` на железе ещё НЕ запускался
Файлы: `kernel/syscall.h`, `kernel/syscall.c` (чистая логика), вход `isr128` в `kernel/isr.S`,
шлюз 0x80 в `kernel/idt.c`, хук `user_on_syscall` в `kernel/user.c`/`interrupts.c`,
три программы в `kernel/usermode.S`, тест `tests/syscall_host.c`.

Что сделано:
- Вход — `int 0x80`, шлюз IDT с DPL=3 (`0xEE`): единственный вектор, доступный из ring3.
  Остальные вызовы из ring3 дают #GP, который ядро перехватывает (Фаза 3).
- Соглашение и номера как в Linux x86_64: rax = номер, аргументы rdi/rsi/rdx, результат в rax, ошибка = -errno.
  Так же будет работать и после перехода на `syscall` и при портировании настоящих программ.
- Вызовы: `read`(0) — stdin пока пуст (EOF), `write`(1) — fd 1 и 2 в буфер вывода ядра, `brk`(12) — настоящий рост
  кучи (страницы отображаются на лету, предел 64 КиБ, при неудаче возвращается текущий brk, как в Linux),
  `exit`(60). Всё остальное — `-ENOSYS`.
- `write` проверяет указатель: диапазон обязан лежать в пользовательской половине, страницы — отображены с битом USER
  (иначе `-EFAULT`; при частичном успехе возвращается число уже записанных байт, как в Linux).
- Состояние процесса сбрасывается между запусками: куча прошлого запуска демонтируется, страницы переиспользуются.

Команда `ring3` теперь делает 6 проверок (3 из Фазы 3 + 3 новых):
4. `hello`: `write("Привет из ring3!\n")` + `brk(0)` + `brk(+8 КиБ)` + запись/чтение кучи + `exit(42)`;
5. `write` с адресом ядра → `-EFAULT` (программа выходит с кодом 14);
6. неизвестный номер → `-ENOSYS` (выход с кодом 38).

Проверено на хосте (`tests/syscall_host.c`, ASan/UBSan, плюс мутации кода): все ветки write/brk/read/exit,
границы пользовательской половины (в том числе когда нижний слой «разрешает всё»), урезание длинного write,
частичная запись, предел brk, откат при нехватке памяти посреди роста, ни одна страница не выдаётся дважды;
число `int 0x80` и текст сообщения в байтах ring3-программ совпадают с тем, что ждут проверки; последовательность
вызовов каждой программы, прогнанная против диспетчера, проходит соответствующий `user_check_*`.
Ядро собирается без предупреждений.

Что НЕ проверено: что процессор выполнит `int 0x80` из ring3 через DPL=3 шлюз, вернёт rax через `iretq` и что
мои три программы в машинном коде делают именно то, что я описал, — на хосте их исполнить нельзя; проверена
только их дизассемблированная форма и модель вызовов. Критерий успеха — «Все 6 проверок прошли» на QEMU/железе.

## Фаза 5 — Мини-libc и первый настоящий ELF ✅ код написан; всё, что выполнимо на хосте, проверено; запуск в ring3 на железе ещё НЕ делался
Файлы: `userland/` (libc.h, crt0.S, sys.c, string.c, malloc.c, fmt.c, stdio.c, user.ld, hello.c, tests/libc_test.c),
`kernel/exec.h`+`exec.c` (загрузчик и стек), `kernel/embed.S` (встраивание hello.elf), `kernel/user.c` (`user_exec`,
`user_run_file`, отчёт), команды `run` и `lima run`, сборка userland в `Makefile`.
Тесты: `tests/exec_host.c`, `tests/fmt_diff_host.c`, `userland/tests/libc_test.c`.

Что сделано:
- **Мини-libc** (не glibc/musl): `_start`, обёртки `read/write/brk/exit`, `string.h` (strlen/strcmp/strncmp/strcpy/strchr/mem*),
  `malloc/calloc/realloc/free` поверх `brk` (куча процесса ограничена ядром 64 КиБ), `atoi/abs`, `printf/snprintf/puts/putchar`
  (`%d %i %u %x %X %o %c %s %p %%`, флаги `- 0 + space #`, ширина, точность, `*`, длины `hh h l ll z`; **без плавающей точки**).
  Нет `errno`, нет `FILE`, нет `open/close` (это Фаза 6).
- **Загрузчик** `exec_load`: проверяет сегменты (образ только в 0x400000..0x10000000, не больше 256 КиБ), создаёт страницы
  (общая страница двух сегментов — одна и записываемая), копирует файловую часть, `.bss` — нули. `exec_build_stack`: `argc/argv/envp/auxv`
  по System V ABI, `rsp` кратен 16. Стек программы — 32 КиБ.
- **Запуск**: `run hello.elf LimonOS` или `lima run hello.elf LimonOS` — файл ищется в текущей папке, затем в `/System`.
  `hello.elf` собирается gcc+ld при `make` и встраивается в ядро (`/System/hello.elf` появляется при загрузке). Любой другой статический
  ET_EXEC ELF под наш набор вызовов можно положить в Memoria и запустить так же.
- Отчёт о запуске: вывод программы, затем код возврата / причина аварии (вектор, RIP, CR2) / таймаут 5 с.
- Команда `ring3` теперь делает 7 проверок (последняя — hello.elf: вывод должен совпасть побайтно).

Проверено на хосте:
- **libc запущена как настоящий процесс Linux**: те же исходники, собранные с `syscall` вместо `int 0x80` (номера read/write/brk/exit у Linux
  такие же), прогнаны как статический ELF: `hello` печатает ожидаемый текст; стресс-тест: 4000 случайных malloc/realloc/free с проверкой
  содержимого и непересечения блоков, переиспользование кучи, `calloc` с переполнением, `memmove` с перекрытием, `snprintf` с усечением.
- **vsnprintf против glibc**: 162 115 сравнений (текст, возвращаемое значение, усечение до 20 байт) — расхождений 0. Тест нашёл две
  настоящие ошибки (`%#o` и `%p` для NULL), обе исправлены.
- **Загрузчик**: настоящий `hello.elf` разобран и загружен, каждая страница сверена байт в байт с файлом; ошибки диапазонов/переполнений/нехватки
  памяти/общих страниц/невыровненных сегментов; стек разобран так, как это делает `_start`. **Сквозной запуск**: образ `hello_host.elf` загружен
  НАШИМ `exec_load` в страницы, отображённые по адресам из ELF, стек построен НАШИМ `exec_build_stack`, управление передано на `e_entry` в
  дочернем процессе — вывод и код возврата совпали с ожидаемыми. Шесть намеренных поломок загрузчика/стека тест поймал.
- Дизассемблер LimonOS-варианта `hello.elf`: нет SSE/MMX, нет `syscall`, нет привилегированных инструкций, 8 входов `int 0x80`.

Что НЕ проверено (нет QEMU/KVM): что ядро на процессоре реально выполнит ELF — `iretq`, `int 0x80` из ELF-кода, возврат; что
`vmm_map` на реальных таблицах Limine создаёт именно такие отображения, как на поддельной памяти. Критерий успеха: `ring3` печатает
«Все 7 проверок прошли», а `run hello.elf LimonOS` печатает текст hello. Если нет — присылай строку `[ПРОВАЛ]` с числами или причину из
сообщения «Не удалось запустить: …» / «программа аварийно остановлена: …».

Ограничения, о которых лучше знать: вывод программы показывается после её завершения, а не по мере работы; stdin пуст (EOF);
программа не может создавать процессы/файлы/сокеты; 5 секунд на запуск; ядро помнит максимум 128 страниц процесса и не освобождает их
(у `pmm` нет `free`) — повторные запуски переиспользуют те же страницы.

## Фаза 6 — Открыть файлы/сокеты через VFS и сеть (готово)
`open/close/lseek` поверх уже готовой VFS (Memoria), `socket/connect` (только
AF_INET/SOCK_STREAM) поверх `net.c`, `read/write` работают и на файлах, и на
сокетах (как fd в Linux). Таблица из 8 дескрипторов на процесс (3 заняты
stdin/stdout/stderr). Отдельно развели «нет данных прямо сейчас» (`EAGAIN`)
и «собеседник закрыл» (0/EOF) — раньше оба давали бы 0 у `tcp_recv`.
Проверено на хосте: вся логика `syscall.c` на поддельных VFS/сети (открытие,
чтение по кускам, lseek с проверкой границ, нехватка дескрипторов, сокет без
connect, оба кода ошибок tcp_connect → errno). НЕ проверено: сам `int 0x80`
с этими номерами на процессоре (нет QEMU) — трюк «та же libc с настоящим
syscall» тут не работает, потому что наша VFS и наш TCP — не Linux.

## Фаза 7 — Настоящая вытесняющая многозадачность (готово, первая итерация)
До этой фазы `user_enter`/`user_resume` (usermode.S) — один глобальный
"корутин": ядро входит в ring3 и блокируется, пока программа не закончится.
Несколько процессов одновременно жить не могли — негде было хранить второй
набор регистров/CR3.

Теперь: `kernel/sched.c` — таблица из `SCHED_MAX_PROC=4` процессов, у каждого
свой PML4 (через `vmm_share_upper_half`, как у Фазы 2), свой `sys_state`
(дескрипторы/куча из Фазы 4/6), свой пул страниц, свой буфер вывода. Таймер
(IRQ0, 100 Гц) при `sched_active()` выполняет НАСТОЯЩЕЕ переключение
контекста прямо внутри обработчика прерывания (`interrupts.c` → `sched_on_timer`):
каждые `QUANTUM_TICKS=5` тиков (~50 мс) сохраняет **полный** снимок регистров
прерванного процесса (`struct regs` — та же структура, что `isr_common`
кладёт на стек и потом забирает через `iretq`, так что её можно просто
перезаписать), переключает `CR3` прямо на лету (это безопасно: стек
обработчика прерывания — общая верхняя половина, видна одинаково при любом
CR3) и возвращает управление `isr_handler` — тот вернётся как обычно, но
`iretq` улетит уже в ДРУГОЙ процесс. Крах (`sched_on_exception`) и `exit()`
(`sched_on_syscall`) снимают процесс и тоже передают управление дальше —
очередь не останавливается из-за одного упавшего процесса. Общий лимит
`TOTAL_TICKS=1000` (10 с) на процесс — страховка от зависшего цикла, отдельно
от квантов чередования.

Команды: `bg <файл> [аргументы]` — поставить ELF в очередь (слот, не
запускает); `jobs` — что в очереди и в каком состоянии; `go` — запустить
очередь, подождать, пока все процессы закончатся (сами, крахом или по
таймауту), напечатать лог чередования квантов (видно, что слоты реально
перемежаются, а не выполняются один за другим) и вывод/итог каждого.

**Честное ограничение этой итерации:** `go` — один блокирующий вызов ядра.
Процессы ВНУТРИ него по-настоящему чередуются (это и есть вытесняющая
многозадачность — таймер реально вмешивается и переключает CR3/регистры),
но из шелла нельзя напечатать `bg a.elf`, затем параллельно потыкать другие
команды, пока a.elf работает в фоне — шелл однопоточный и ждёт `go` целиком.
Чтобы процессы жили между командами шелла по-настоящему «в фоне», нужно
встроить вызов планировщика в главный цикл ядра (там же, где опрашивается
клавиатура) — это следующий шаг, не этот.

Проверено на хосте: не проверялось отдельно (`sched.c`, как и `user.c`,
исключён из хост-сборки — весь смысл в реальных `iretq`/`cr3`/таймере,
которых на хосте нет; `tests/hoststubs.c` даёт только заглушки, чтобы
собиралась сборка снимков рабочего стола). Весь остальной хост-набор
(Фазы 1-6, игры, FAT32, VFS, снимки рабочего стола) по-прежнему проходит
без изменений — это и есть доказательство, что Фаза 7 ничего не сломала.
НЕ проверено (нужен QEMU): сам факт, что переключение CR3 внутри обработчика
прерывания не роняет ядро, что два процесса реально чередуются на экране,
а не просто один долго думает. Критерий успеха: `bg hello.elf A`, `bg
hello.elf B`, `go` печатают лог чередования НЕ в виде «0 0 0 0 1 1 1 1»
(это было бы последовательным выполнением), а вперемешку — «0 1 0 1 0 1...».

## Почему даже после Фазы 7 это не «apt install nmap» в линуксовом смысле
nmap, python, git, msfconsole, wireshark написаны под glibc/POSIX с сотнями
системных вызовов и библиотек (libpcap, OpenSSL, zlib, Qt...), которых у нас
всё ещё нет. Многозадачность Фазы 7 не меняет этого: можно крутить сразу
несколько СВОИХ процессов, но каждый всё ещё обязан быть собран под нашу
мини-libc и наш узкий набор вызовов. Довести до реального запуска *конкретно
настоящих* nmap/python — это либо (а) написать достаточно совместимый с
Linux ABI слой (огромный объём работы, по сути собственный Linux-совместимый
рантайм), либо (б) пересобрать каждую программу под нашу мини-libc, выкинув
то, чего у нас нет (для nmap — переписать работу с сетью на наш `net.c`, для
python — это по сути отдельный интерпретатор, который надо портировать как
целый проект).

Короче: Фазы 1-7 дают честный, работающий фундамент, первый реальный запуск
*своих* простых бинарей и настоящую (хоть и первую, ограниченную) многозадачность
между ними. Они не обещают запуск настоящего nmap/python «как в Termux» — это
была бы снова та же ложь, только отложенная на потом.
